# Port iOS PR #145 — NIP-22 reply parity (counts + notification labels)

Follow-up to #767 (stacked on `feat/nip22-mixed-threads`, which supplies the parsing layer). iOS reference: squash commit `ad1ecc17` — `EngagementRepository.swift`, `EventStore.swift`, `NotificationRepository.swift`, `NotificationItem.swift`; reasoning in `docs/nip22-reply-parity.md`.

## What iOS #145 did (decisions that carry over)

- Count kind-1111 comments as replies everywhere counting happens, **attributed to the immediate parent** (lowercase `e`) — a deep comment (`E` = root, `e` = mid-thread) is NOT a direct reply to the root.
- Dedup by event id before any increment ("dedup by delivery, not by intent").
- Label comment notifications by the **parent's kind** — a field (`parentKind` from the lowercase `k` tag), not a new notification type: "replied to your comment" vs "your note" vs "in your thread".
- Publishing keeps the target kind (already ported in #767); feed stays 1111-free (web already matches).

## What the web already has (no work needed)

Notification live+backfill subs already admit 1111 via `#P`/`#p` (`notificationStore.ts:237,239`); click-through already navigates by the reply's own id; recipe-side counting already uses `#A`.

## Changes

### 1. Counting — three filters + kind-aware attribution

- **`src/lib/engagementTarget.ts`**: `getEngagementTargetId(tags, kind?)` and `engagementTargetsNote(tags, kind, eventId)` gain a kind-1111 branch: the target is the **lowercase `e` only** (uppercase `E` is the root — a nested comment must not count toward it). Kind-1 behavior unchanged. NIP-10 markers never apply to 1111.
- **`src/lib/engagementCache.ts`**:
  - Live sub filter (:719-722): `kinds: [7, 6, 9735, 1, 1111]`.
  - `applyEngagementEvent` (:353-378): `case 1111` alongside `case 1` → `comments.count++`, same `engagementTargetsNote` gate (now kind-aware). Existing id-dedup (`processedEventIds`) provides the by-delivery dedup.
  - Batch sub (:1431-1434): same kinds; routing (:1448-1452) passes `event.kind` to `getEngagementTargetId`.
- **`src/lib/countQuery.ts` `getEngagementCounts` (:613)**: comment count becomes the **sum** of `{kinds:[1], '#e':[id]}` + `{kinds:[1111], '#e':[id]}` fetched in parallel (mirrors `getAddressableEngagementCounts`'s summing pattern). `#e` on 1111 matches only direct comment children (nested comments carry `e` = parent comment), which is exactly iOS's immediate-parent attribution — achievable with NIP-45 after all.
- **Server fast paths**: `src/routes/api/counts/[eventId]/+server.ts` (:206-209) and `src/routes/api/counts/batch/+server.ts` (:196-199) get the same additional 1111-`#e` count folded into the comment total.
- **`src/components/Recipe/TotalComments.svelte`** fast path (:30): note branch sums both counts (subscription path already sees 1111 via #767's filters; keep the kind-5 skip).

Not ported (documented in the PR): iOS's blocked-author count gating (web engagement counting has no mute/block gate today — display filtering handles it); the EventStore disk-seed (web's engagement persistence is refreshed by these same paths).

### 2. Notifications — labels

- **`src/lib/notificationStore.ts` `parseNotification` case 1111 (:568-578)**:
  - `targetEventId`: lowercase `e` **fallback uppercase `E`** (addressable-root comments have no `e`; iOS `classifyComment` uses `parentId ?? rootId`).
  - New optional `Notification.parentKind?: number` from the lowercase `k` tag, and `parentAuthorIsMine?: boolean` from `p` == own pubkey (web's stand-in for iOS's `selfEventIds` check — the `p` tag names the parent's author, which is exactly the distinction needed).
  - Coordinate-only comments (no `e` and no `E`) keep today's behavior (kept, opened by their own id) rather than iOS's drop — the web's click-through can handle them.
- **Label sites** (web keeps its "replied to …" tense):
  - `NotificationBell.svelte` (:188-189) + `NotificationPanel.svelte` (:70-71) + push body (`notificationStore.ts:646-651`): `parentKind === 1111` → "replied to your comment"; else "replied to your post"; when `parentAuthorIsMine` is false but the row exists (matched via `#P`) → "replied in your thread".
  - `src/routes/notifications/+page.svelte` (:815): the page already fetches ctx with `kind` — extend the existing author-name logic: ctx is a comment (`ctx.kind === 1111`) → "replied to {name}'s comment" / "your comment" when the parent author is the user; otherwise "post".
- Own-event registry / cold-start hydration ports are unnecessary: the web's `#p` filter already matches replies to freshly published comments, and there is no disk-hydrated notification store.
